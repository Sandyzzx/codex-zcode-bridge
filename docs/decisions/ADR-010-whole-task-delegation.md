# ADR-010：整任务委派（Whole-Task Delegation）

> Status: DECISION
> Decision: Accepted（用户于 2026-10-18 提议以整任务委派替代微任务默认）
> Date: 2026-10-18

## Context

现有 Skill 把 ZCode 描述为执行一个“有明确边界任务”的 worker，但没有规定任务粒度；实践中容易把一个完整成果拆成连续的文件级、函数级或步骤级任务。每次派发都会带来新的上下文装载、代码库重复调查和协调开销，也会让 Master 退化为逐步指挥者。`zcode_continue` 的语义是同一任务/会话的新 attempt，如果用它推进“下一步实现什么”，会把返工通道变成微任务调度器。

## Decision

1. **默认 Whole-task。** 把一个可独立验收的完整开发成果作为单个 ZCode 任务派发；Worker 自主完成调查、内部规划、实现、测试、失败修复、重测和交付报告。
2. **按交付成果划分粒度。** 不以文件数、函数数、代码行数、prompt 长短或内部步骤数量判断是否拆分。只有多个成果可以独立验收、存在真实依赖、权限边界不同或执行预算确实需要分开时，才拆成多个 Worker 任务。
3. **Master 保留决定权。** 目标、关键约束、已批准的架构决定、交付物、验收标准和最终接收由 Master 负责；Master 不规定 Worker 的详细内部实现步骤，除非该步骤本身属于必要约束。
4. **Worker 拥有实现自主权。** 在授权边界内，Worker 自行决定修改哪些文件、采用什么内部实现、补充哪些测试，以及测试失败后的修复与重测。低影响实现选择自行决定并在报告中说明假设。
5. **Decision Boundary。** Worker 只在外部合同变化、重大架构改变、互相冲突的要求、权限扩大或无法自行解决的阻塞时请求 Master。需要决定时记录具体问题、设置 `needs_master_decision=true`，并继续不依赖该决定的工作。
6. **续作不是常规调度。** `zcode_continue` 只用于验收返工、关键决定补充、受控中断恢复或报告修复；不用于推进正常实现的下一步微任务。返工应集中整理全部失败证据后一次提出。
7. **监控被动化。** Worker 正常实现、测试和修复时只观察进度；长时间无输出先检查业务事件、执行目录文件变化、交互、心跳和进程身份，不立即取消或重派；完整交付后再独立验收。
8. **模式分级。** Whole-task 为默认；跨多个独立交付目标的长期项目可选 Ledger（Project-task）；Micro-task 不作为默认；Autonomous-project 暂不默认支持。
9. **预算边界。** 单次执行默认 60 分钟、最长 4 小时。完整任务可能超出预算时，先拆成可独立验收的交付单元或明确延长预算，不通过无限自动续作绕开限制。

## Rationale

完整任务委派让 ZCode 使用其原生 Coding Agent 能力完成内部计划、跨文件修改和测试闭环，减少重复装载上下文与协调次数；Master 的工作集中在目标定义、关键决定和独立验收，仍然控制外部合同与最终质量。把 `zcode_continue` 限定为返工、决定、恢复和报告修复，避免同一个 delivery 被拆成大量短 attempt。

## Consequences

- Skill 的派发与监控规则、Worker prompt 同步更新；MCP 工具名和 schema 不变。
- Ready Gate 仍然要求目标、实际执行目录、路径边界、验收标准、测试资源和预算明确；整任务委派不等于无限授权。
- Worker 的完成报告仍只是执行证据，Master 必须独立检查 diff、文件和测试后才能接收。
- Ledger 仍是可选的项目级路径，不成为每次派发的必经步骤；Project-task 只在多个独立交付目标需要依赖和长期追踪时使用。
- 单个完整任务可能运行更久；超时仍按现有 attempt 规则终止并保留证据，续作需经过检查后显式发起。
